# 测试树场景需求文档

## 1. 文档目标

本文档用于把当前“左侧树 + 右侧详情”的实际业务场景整理成统一、可执行、可校验的需求描述，为后续设计文档、技能化封装和测试代码提供同一份来源。

## 2. 业务目标

系统需要用一棵复杂树来统一承载以下对象及其关系：

- 空间
- 产品
- 容器版本
- 基线版本
- 测试版本 / 执行版本
- 用例容器
- 测试场景
- 测试项 / 特性
- 目录
- 基线用例
- 执行用例

系统需要支持这些对象的层级管理、详情查看、动态字段扩展、节点创建/修改/删除/移动、特性转目录等操作，并且能通过多种接口组合支撑复杂的右侧详情区域。

## 3. 术语统一

当前描述中存在“测试版本”和“执行版本”两个说法。本文档做如下约定：

- `执行版本`：本文档中的统一术语
- `测试版本`：在未澄清前，视为 `执行版本` 的别名

如果后续产品确认两者不是同一个概念，需要再拆分类型与规则。

## 4. 树节点核心字段

每个树节点至少具备以下核心字段：

| 字段 | 说明 |
| --- | --- |
| `longIdPath` | 长 ID 路径，使用 `/` 分隔 |
| `shortId` | 短 ID，用于短链路展示或跨系统引用 |
| `currentLevelId` | 当前层级 ID，通常应与 `longIdPath` 最后一段一致 |
| `type` | 节点类型 |
| `name` | 节点名称 |
| `number` | 编号 |

此外，节点还具备：

- 大量扩展字段，当前预估 100+，并且允许后续继续动态增加
- 类型特有字段，例如状态、排序、路径、来源、转换标记、统计信息等
- 右侧详情区使用的补充字段，例如描述、责任人、时间、标签、关联对象等

## 5. 节点类型

当前需求下至少包含以下节点类型：

| 中文名 | 建议类型值 |
| --- | --- |
| 空间 | `space` |
| 产品 | `product` |
| 容器版本 | `container_version` |
| 基线版本 | `baseline_version` |
| 执行版本 | `execution_version` |
| 用例容器 | `case_container` |
| 测试场景 | `test_scene` |
| 特性 | `feature` |
| 目录 | `directory` |
| 基线用例 | `baseline_case` |
| 执行用例 | `execution_case` |

## 6. 层级关系需求

### 6.1 顶层关系

- 空间下可以直接挂：
  - 产品
  - 容器版本
  - 基线版本

### 6.2 产品下关系

- 产品下面可挂：
  - 容器版本
  - 基线版本

### 6.3 容器版本与基线版本关系

- 容器版本与基线版本是同级对象
- 当前业务描述中，容器版本与基线版本下都可以出现：
  - 用例容器
  - 执行版本

但这里存在一个待确认点：

- “基线版本直接挂一个用例容器和多个执行版本”是明确规则
- “容器版本是否也遵循同样的数量规则”尚未完全明确

因此本文先做以下需求假设：

- 基线版本：必须挂且仅挂一个用例容器，可挂多个执行版本
- 容器版本：可挂用例容器和执行版本，数量规则待业务确认

### 6.4 基线版本下关系

- 基线版本直接挂：
  - 一个用例容器
  - 多个执行版本

- 基线版本的用例容器下挂：
  - 目录
  - 特性

- 目录与特性同级
- 目录和特性下可继续嵌套：
  - 目录
  - 特性
  - 用例

- 基线版本分支下的用例都归类为 `基线用例`

### 6.5 执行版本下关系

执行版本存在二选一模式：

1. 挂单个容器版本
2. 挂多个场景

两种模式不能同时存在。

进一步约束如下：

- 场景和用例容器属于同级层级概念
- 场景下不能一开始直接建目录
- 场景下必须先建特性，再将特性转为目录
- 场景分支下的目录和特性都可以挂执行用例
- 执行版本分支下的用例都归类为 `执行用例`

### 6.6 场景下目录约束

这里的关键点不是纯静态树形关系，而是创建流程约束：

- 场景的直接子节点初始只能创建 `特性`
- 某个特性允许执行“转目录”操作
- 转换后，在树快照中可能出现“场景直接挂目录”的结果

因此系统需要同时表达：

- 节点当前类型
- 节点是否由特性转换而来

## 7. 右侧详情需求

右侧详情区至少需要支持以下模式：

- 查看和编辑当前节点的详情字段
- 按当前节点上下文显示子节点列表或统计信息
- 基于节点类型展示不同字段组
- 支持 100+ 动态字段的渲染、校验、显示与扩展

右侧详情区应至少具备以下能力：

- 根据 `type` 切换字段布局
- 根据上下文区分基线用例与执行用例
- 支持新增动态字段定义后自动展示
- 支持接口返回部分字段和全量字段两种模式

## 8. 动态字段需求

系统存在大量可扩展字段，因此不能把全部字段硬编码在节点表结构或前端表单中。

必须支持：

- 固定核心字段 + 扩展字段的混合模型
- 不同类型节点有不同字段定义
- 新增字段不要求改动所有节点类型代码
- 右侧详情区按字段定义动态渲染
- 查询接口按需要返回精简字段或全量字段

## 9. 操作需求

系统需要支持以下操作：

- 查询树
- 查询节点详情
- 创建节点
- 修改节点
- 删除节点
- 移动节点
- 调整排序
- 特性转目录
- 执行版本模式切换或校验

其中需要重点校验：

- 父子关系是否合法
- 执行版本模式是否冲突
- 基线版本下是否存在唯一用例容器
- 场景下目录是否由特性转换而来
- 用例类型是否和所在上下文一致
- `longIdPath` 是否和父子关系一致

## 10. 非功能需求

- 树结构规则需要可配置、可测试
- 文档、skill、测试代码需要共用同一套术语
- 校验逻辑要能脱离 UI 单独运行
- 后续新增节点类型时，尽量通过规则扩展而非重写全量逻辑

## 11. 已识别歧义与待确认项

当前需求仍有以下待确认点：

1. `测试版本` 与 `执行版本` 是否完全同义
2. `容器版本` 直接挂用例容器后，其中的用例应归为哪一类
3. `场景和用例容器同级` 是概念同级，还是允许作为相同父节点的直接子节点
4. `测试项` 与 `特性` 是否同义
5. 动态字段的定义来源是配置中心、数据库表，还是接口动态下发

在未进一步澄清前，本文及配套设计采用保守假设，并在设计文档中显式标注。
