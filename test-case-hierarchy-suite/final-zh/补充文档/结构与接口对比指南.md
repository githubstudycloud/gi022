# 结构与接口对比指南

## 1. 这份文档解决什么问题

这份文档不是给 AI 用的，而是给人看的。
目的有三个：

- 把当前已经确认过的层级结构设计写成容易阅读的样子
- 把接口设计补齐到“可以拿来讨论和对比”的程度
- 给后续不同业务的人一个统一比对框架，快速看出哪些是通用骨架，哪些是业务差异

如果你后面要把这套思路迁移到“目录树”“组织树”“知识分类树”“商品分类树”“菜单权限树”等场景，这份文档就是对比基线。

## 2. 当前已确认的测试层级结构骨架

### 2.1 节点类型

当前测试层级里，核心节点类型如下：

| 节点类型 | 说明 |
| --- | --- |
| `space` | 空间 |
| `product` | 产品 |
| `baseline_version` | 基线版本 |
| `container_version` | 容器版本，当前按基线侧结构处理 |
| `execution_version` | 执行版本 |
| `case_container` | 用例容器 |
| `test_scene` | 测试场景 |
| `directory` | 目录 |
| `feature` | 特性 |
| `baseline_case` | 基线用例 |
| `execution_case` | 执行用例 |

### 2.2 顶层骨架

可读版结构如下：

```text
space
├─ product
│  ├─ baseline_version
│  └─ container_version
├─ baseline_version
└─ container_version
```

### 2.3 基线侧结构

`baseline_version` 和 `container_version` 当前按同一套结构规则处理：

```text
baseline_version / container_version
├─ case_container
│  ├─ directory
│  │  └─ baseline_case
│  └─ feature
│     └─ baseline_case
└─ execution_version
```

硬规则：

- `baseline_version` 下面必须且只能有一个直属 `case_container`
- `container_version` 下面必须且只能有一个直属 `case_container`
- 两者都不能直接挂 `directory`、`feature`、`test_scene`、`baseline_case`、`execution_case`
- 两者的 `case_container` 下面是基线侧内容

### 2.4 执行侧结构

`execution_version` 只允许直属一个 `case_container`，但有两种锁定形态。

#### 形态 A：`container_direct`

```text
execution_version
└─ case_container
   ├─ directory
   │  └─ execution_case
   └─ feature
      └─ execution_case
```

#### 形态 B：`scene_grouped`

```text
execution_version
└─ case_container
   └─ test_scene
      ├─ directory
      │  └─ execution_case
      └─ feature
         └─ execution_case
```

硬规则：

- `execution_version` 下面必须且只能有一个直属 `case_container`
- `case_container` 下不能直接建用例
- `test_scene` 下不能直接建用例
- 用例只能建在 `directory` 或 `feature` 下
- 执行版本一旦进入某种形态，就不能再切换到另一种形态

### 2.5 目录与特性的关系

当前设计里：

- `directory` 与 `feature` 等价
- 两者都可以继续挂 `directory`
- 两者都可以继续挂 `feature`
- 两者都可以挂用例
- 两者允许互改 `type`
- 当前默认理解是：互转时只改 `type`，路径和主键保持稳定

## 3. 当前结构设计为什么适合做“对比基线”

这套设计的价值不只是服务测试树。
它还抽出了很多通用层级业务都会遇到的问题：

- 顶层容器和中间层容器怎么区分
- 哪些节点只能唯一
- 哪些节点只能作为结构节点，不能直接挂业务叶子
- 业务叶子是按“最近上下文”决定类型，还是固定类型
- 一棵树里是否允许存在多种组织形态
- 某些兄弟节点是否可以等价互转

这几个点，几乎就是不同树形业务最常见的分歧来源。

## 4. 面向人的接口设计补充

下面的接口设计不是后端代码定稿，而是“讨论和比对业务差异”的统一接口骨架。

### 4.1 树查询接口

#### 1. 查询整棵树或某个根节点下的树

```http
GET /tree/nodes
```

建议入参：

| 参数 | 说明 |
| --- | --- |
| `rootType` | 根节点类型，可选 |
| `rootId` | 根节点 ID，可选 |
| `expandDepth` | 默认展开层级，可选 |
| `keyword` | 树节点搜索关键字，可选 |

建议返回：

- 节点基础字段
- 子节点摘要
- 可展开标记
- 当前节点摘要信息

#### 2. 查询某个节点的直属子节点

```http
GET /tree/nodes/{path}/children
```

这个接口适合：

- 懒加载树
- 局部刷新
- 拖拽后重拉某个父节点

### 4.2 详情查询接口

#### 1. 查询节点详情

```http
GET /tree/nodes/{path}/detail
```

建议返回分成三层：

- 基础标识字段
- 结构控制字段
- 业务字段与动态字段

#### 2. 查询节点可执行动作

```http
GET /tree/nodes/{path}/actions
```

建议返回：

- 是否可新建目录
- 是否可新建特性
- 是否可新建用例
- 是否可删除
- 是否可移动
- 是否可互转 `directory/feature`

这个接口特别适合“不同业务规则差异化很大，但前端要统一渲染”的场景。

### 4.3 创建和修改接口

#### 1. 新建节点

```http
POST /tree/nodes
```

建议入参：

| 字段 | 说明 |
| --- | --- |
| `parentPath` | 父节点路径 |
| `targetType` | 目标节点类型 |
| `name` | 节点名称 |
| `number` | 节点编号 |
| `extFields` | 扩展业务字段 |
| `meta` | 上下文控制信息 |

#### 2. 更新节点

```http
PATCH /tree/nodes/{path}
```

建议只允许更新：

- 可编辑基础字段
- 业务字段
- 可修改的控制字段

不要让这个接口承担“变更父子关系”的职责。

### 4.4 结构变更接口

#### 1. 移动节点

```http
POST /tree/nodes/{path}/move
```

适合处理：

- 拖拽换父节点
- 同级调序
- 跨分支迁移

#### 2. 重排同级顺序

```http
POST /tree/nodes/{path}/reorder
```

适合处理：

- 仅同级排序
- 不改变父子关系

#### 3. 目录与特性互转

```http
POST /tree/nodes/{path}/convert-to-feature
POST /tree/nodes/{path}/convert-to-directory
```

如果换成其他业务，也可以把这类接口理解为“同能力节点的 type 互转接口”。

### 4.5 校验接口

#### 1. 父子关系校验

```http
POST /tree/validate/parent-child
```

适合：

- 创建前校验
- 拖拽前校验
- 批量导入前校验

#### 2. 执行版本形态校验

```http
POST /tree/validate/execution-shape
```

适合：

- 校验 `container_direct`
- 校验 `scene_grouped`
- 防止两种形态混用

#### 3. 整棵树校验

```http
POST /tree/validate/tree
```

适合：

- 导入树结构后统一校验
- 发布前统一校验
- 巡检和脚本验证

## 5. 不同业务对比时，重点看哪些差异

后续让别人拿这份文档和其他业务做对比时，建议重点看下面这几类差异。

### 5.1 节点类型差异

要比对：

- 哪些节点是结构节点
- 哪些节点是业务叶子
- 哪些节点是上下文节点
- 哪些节点需要唯一

示例：

| 业务 | 结构节点 | 业务叶子 | 上下文节点 |
| --- | --- | --- | --- |
| 测试层级 | `case_container`、`test_scene`、`directory`、`feature` | `baseline_case`、`execution_case` | `baseline_version`、`container_version`、`execution_version` |
| 组织架构 | `company`、`department`、`group` | `employee` | `company`、`region` |
| 商品分类 | `catalog`、`category`、`sub_category` | `sku` 或 `spu` | `brand`、`store` |

### 5.2 父子关系差异

要比对：

- 是否允许唯一直属容器
- 是否允许直接挂叶子节点
- 是否有场景中间层
- 是否允许跨层级混挂

### 5.3 叶子类型判定差异

测试树最特别的一点是：

- 叶子类型不是固定的
- 而是由最近版本上下文决定

别的业务可能不同：

- 商品树里叶子通常固定是 `sku`
- 组织树里叶子通常固定是 `employee`
- 权限树里叶子可能固定是 `menu` 或 `permission`

这就是一个最重要的业务差异项。

### 5.4 详情面板差异

要比对：

- 右侧面板显示的是当前节点详情，还是当前节点下的子记录
- 是否按节点类型动态切换字段组
- 是否存在只读字段、动态字段、业务字段分区

### 5.5 接口职责差异

要比对：

- 是否把“结构变更”和“内容编辑”拆成不同接口
- 是否需要单独的动作权限接口
- 是否需要单独的规则校验接口
- 是否需要独立的字段定义接口

## 6. 给他人使用这份文档的推荐比对模板

别人要拿当前测试层级和另一个业务做对比时，建议直接套下面这个模板：

```md
# XXX 业务与测试层级对比

## 1. 业务目标

## 2. 节点类型对比

## 3. 父子关系对比

## 4. 是否存在唯一容器节点

## 5. 是否存在上下文决定叶子类型

## 6. 右侧详情模式对比

## 7. 接口职责对比

## 8. 可以复用的部分

## 9. 不能直接复用、必须改造的部分
```

## 7. 结论

如果后面你还要继续扩这套材料，我建议把所有“面向人的对比文档”都以这份为母版来扩展。

这样做的好处是：

- 结构规则有固定讲法
- 接口职责有固定讲法
- 不同业务之间能快速看出差异
- AI 在后面继续改 skill 或改设计文档时，也更容易对齐你的口径
