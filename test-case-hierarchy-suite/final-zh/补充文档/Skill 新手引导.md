# Skill 新手引导

## 1. 这份文档给谁看

这份文档是给第一次用这套方法的人看的。
它回答三个实际问题：

- 这两个 skill 到底怎么用
- 我应该给 AI 什么资料，才能让它做出真正可用的 skill
- 如果我是新手，第一次应该按什么步骤走

## 2. 你现在手里有哪些 skill

当前已经准备好的中文 skill 有两个：

### 2.1 `baseline-execution-case-guide`

定位：

- 这是一个业务专项 skill
- 只负责基线用例和执行用例相关的问题

适合问它：

- 这个节点到底应该是 `baseline_case` 还是 `execution_case`
- 这个地方能不能新建用例
- 查询范围应该挂在哪个父节点下
- 右侧详情应该显示哪些字段

### 2.2 `hierarchy-skill-builder-guide`

定位：

- 这是一个元 skill
- 不是直接回答业务，而是教 AI 怎样把一套层级业务材料做成真正的 skill

适合问它：

- 我要新做一个组织树 skill，应该怎么拆
- 哪些内容放在 `SKILL.md`，哪些放 `references`
- 我应该给 AI 准备哪些资料
- 怎么把现有 broad skill 拆成更聚焦的子 skill

## 3. skill 的基本使用方式

### 3.1 最简单的用法

你直接在提问时点名 skill：

```text
Use $baseline-execution-case-guide 帮我判断这个节点下面应该创建 baseline_case 还是 execution_case
```

或者：

```text
Use $hierarchy-skill-builder-guide 根据我给的需求文档，帮我生成一个新的层级业务 skill
```

### 3.2 实际推荐的用法

不要只说“帮我做一个 skill”，而要把任务说清楚。

更推荐这样问：

```text
Use $hierarchy-skill-builder-guide。
我现在有一套部门管理树，左边树右边详情。
请根据我提供的需求、结构样例和接口草案，帮我生成一个聚焦在“部门节点新增、移动、删除规则”的 skill。
```

这样 AI 才会知道：

- 这是层级业务
- 目标不是整个领域，而是一个聚焦子领域
- 你已经给了源材料
- 它需要产出的不是普通回答，而是真正的 skill 文件

## 4. 想让 AI 创建“实际 skill”，你至少要提供什么资料

很多 skill 之所以做不实，不是 AI 不会写，而是输入资料不够。
如果你要 AI 产出真正能落地的 skill，最少要给下面这五类材料。

### 4.1 业务目标

你要说清楚：

- 这个 skill 是解决什么问题的
- 给谁用
- 用在什么场景
- 什么问题会触发它

最差的说法：

```text
帮我做个 skill
```

更好的说法：

```text
帮我做一个组织树专项 skill，用来回答“哪些节点能新增部门、哪些节点能删除、哪些节点不能直接挂员工”这类问题。
```

### 4.2 结构资料

你至少要给 AI 下面之一：

- 树形结构示例
- 节点类型清单
- 父子关系矩阵
- 唯一性和禁止挂载规则

如果没有这些，AI 只能写出很空的 skill。

### 4.3 接口资料

你至少要给下面之一：

- 已有接口清单
- 草拟 API 设计
- 请求/响应示例
- 前端调用方式

原因很简单：

- skill 最终不是只解释规则
- 它往往还要指导实现、对接和回答接口问题

### 4.4 字段资料

你至少要告诉 AI：

- 哪些是基础字段
- 哪些是动态字段
- 哪些字段只读
- 哪些字段在详情显示
- 哪些字段参与校验

### 4.5 样例资料

最好至少提供一组：

- 正确样例
- 错误样例
- 边界样例

这是让 skill 从“抽象规则”变成“可验证经验”的关键。

## 5. 推荐你给 AI 的资料包结构

如果你后面要让 AI 再做新的 skill，建议你按下面这个目录结构准备材料：

```text
your-business/
├─ requirements.md
├─ design.md
├─ structure-examples.md
├─ interface-draft.md
├─ field-groups.md
├─ fixtures/
│  ├─ valid-example.json
│  ├─ invalid-example-1.json
│  └─ invalid-example-2.json
└─ notes.md
```

这套结构的好处是：

- AI 很容易知道去哪里找什么
- 后续 skill 可以持续迭代
- 别人接手时也看得懂

## 6. 新手第一次创建 skill 的推荐步骤

下面是一套真正适合新手照着做的顺序。

### 第一步：先别急着让 AI 写 skill

先整理三件事：

1. 你的业务到底要解决什么问题
2. 这个问题是不是一个稳定、可复用的问题
3. 你要的是“大而全 skill”还是“聚焦专项 skill”

如果这一步不做，AI 很容易把 skill 写得过大、过空、不可复用。

### 第二步：先整理最小资料包

最低建议至少有：

- 一份需求说明
- 一份结构样例
- 一份接口草案

如果能再补上字段分组和正反样例，会明显更稳。

### 第三步：明确这次 skill 的范围

你要直接告诉 AI，这次 skill 的边界。

例如：

- 只做“节点新增规则”
- 只做“目录与特性互转规则”
- 只做“右侧详情字段分组”
- 只做“基线/执行用例上下文判断”

不要让 AI 同时覆盖整个领域，除非你真的准备做一个 broad skill。

### 第四步：点名用元 skill 来创建

可以直接这样发起：

```text
Use $hierarchy-skill-builder-guide。
我提供了一套层级业务资料，请你帮我创建一个新的 skill。
目标范围是：XXX。
请优先做聚焦 skill，不要做大而全。
```

### 第五步：把资料明确贴给 AI

推荐按这个顺序给：

1. 业务目标
2. 结构规则
3. 结构样例
4. 接口草案
5. 字段说明
6. 正反样例

### 第六步：要求 AI 产出这些文件

你可以明确要求：

- `SKILL.md`
- `agents/openai.yaml`
- 必要的 `references/*.md`
- 如果需要，再加 `scripts/`

这样 AI 就不会只给你一段解释，而是真正开始落 skill 文件。

### 第七步：让 AI 先做第一版，再人工审

第一次不要追求完全正确。
先看三件事：

- 触发描述准不准
- 工作流顺不顺
- reference 拆分合理不合理

如果这三件都对了，后面改细节就很快。

## 7. 一个可直接复用的提问模板

你后面可以直接复制下面这个模板，用来让 AI 创建新的实际 skill。

```text
Use $hierarchy-skill-builder-guide。

我想创建一个新的层级业务 skill。

目标业务：
- [这里写业务名称]

这次 skill 的范围：
- [这里写聚焦目标，例如：节点新增与删除规则]

触发场景：
- [这里写用户会怎么问]

我提供的资料：
- requirements.md：业务目标和规则
- structure-examples.md：结构样例
- interface-draft.md：接口草案
- field-groups.md：字段分组
- fixtures/*.json：正反样例

要求你输出：
- 一个可直接使用的 SKILL.md
- 一个 agents/openai.yaml
- 必要的 references 文件

要求：
- 优先做聚焦 skill
- 不要保留 TODO
- 说明哪些资料还不足
```

## 8. 什么时候资料算“不够”

如果你只给下面这种信息，通常不够：

- 只有一句业务描述
- 只有一个页面截图
- 只有几个字段名
- 没有结构规则
- 没有父子限制
- 没有示例路径

这种情况下，AI 最多只能生成“格式上像 skill”的东西，很难生成“真正可用的 skill”。

## 9. 给新手的最终建议

如果你是第一次做，最稳的方式不是一次做大，而是按这个顺序推进：

1. 先做一个专项 skill
2. 跑一轮实际问答
3. 找出哪里回答不稳
4. 再补 reference 和样例
5. 最后再考虑做 broad skill

对新手来说，“先做一个小而准的 skill”，远比“一次做一套大而全 skill”成功率高。
