# API Design Standards

## 1. URL Design

### Rules

| Rule | Example |
|------|---------|
| Resource names are plural nouns (kebab-case) | `/api/v1/users`, `/api/v1/order-items` |
| Version prefix is mandatory | `/api/v1/...` |
| Actions expressed via HTTP method, not URL | `DELETE /users/{id}` not `/users/{id}/delete` |
| Sub-resources via path nesting (max 2 levels) | `/users/{id}/roles` |
| State transitions via PATCH + descriptor | `PATCH /users/{id}/disable` |

### HTTP Method Semantics

| Method | Use case | Body | Success Code |
|--------|----------|------|--------------|
| GET | Read (list or single) | No | 200 |
| POST | Create | Yes | 201 |
| PUT | Full update (replace) | Yes | 200 |
| PATCH | Partial update or state change | Yes | 200 |
| DELETE | Delete | No | 200 or 204 |

---

## 2. Response Format

All responses use `Result<T>`:

```json
{
  "code": 200,
  "message": "Success",
  "data": { ... },
  "timestamp": 1710000000000
}
```

### Paginated Response

```json
{
  "code": 200,
  "message": "Success",
  "data": {
    "records": [ ... ],
    "total": 100,
    "page": 1,
    "size": 20
  }
}
```

### Error Response

```json
{
  "code": 42201,
  "message": "Username is required; Password must be at least 8 characters",
  "timestamp": 1710000000000
}
```

## 3. Error Codes

### HTTP Layer (transport)

| Code | Meaning |
|------|---------|
| 200 | Success |
| 201 | Resource created |
| 400 | Bad request (malformed) |
| 401 | Unauthenticated |
| 403 | Unauthorized (forbidden) |
| 404 | Resource not found |
| 422 | Validation failed |
| 429 | Rate limit exceeded |
| 500 | Server error |

### Business Layer (domain-specific)

| Code | Meaning |
|------|---------|
| 40101 | Username or password incorrect |
| 40102 | Token expired |
| 40103 | Token invalid |
| 40301 | Account disabled |
| 40401 | User not found |
| 40901 | User already exists |
| 42201 | Parameter validation failed |

### Business Code Naming Convention

```
{HTTP_STATUS_PREFIX}{SERVICE_PREFIX}{SEQUENCE}
40401 = 404 (not found) + 01 (first not-found code in service)
40901 = 409 (conflict)  + 01 (first conflict code)
```

## 4. Pagination Convention

Query parameters for paginated list endpoints:

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `page` | Integer | 1 | Page number (1-based) |
| `size` | Integer | 20 | Items per page (max 100) |
| `sort` | String | — | Sort field (e.g. `createTime`) |
| `order` | String | `desc` | Sort direction: `asc` or `desc` |
| `keyword` | String | — | Full-text search keyword |

---

## 5. Authentication

All protected endpoints require:

```http
Authorization: Bearer <access_token>
```

Token refresh:
```http
POST /api/v1/auth/refresh
Body: { "refreshToken": "..." }
```

---

## 6. Versioning Strategy

- Current version: `v1`
- Breaking changes require a new version (`v2`)
- Non-breaking additions (new optional fields) do NOT require a new version
- Deprecated versions are supported for **2 minor releases** after deprecation notice

---

## 7. OpenAPI Documentation

All endpoints MUST have:

```java
@Tag(name = "Users")                    // Controller level
@Operation(
    summary = "Get user by ID",         // Short description
    description = "Returns full user profile. Admin can access any user."
)
@ApiResponse(responseCode = "200", description = "User found")
@ApiResponse(responseCode = "404", description = "User not found")
```

Access Swagger UI at: `http://localhost:{port}/swagger-ui.html`

---

## 8. Request/Response Headers

### Request Headers

| Header | Required | Description |
|--------|----------|-------------|
| `Content-Type` | Yes (for body) | `application/json` |
| `Authorization` | Yes (protected) | `Bearer <token>` |
| `X-Request-Id` | No | Client trace ID; generated by server if absent |

### Response Headers

| Header | Description |
|--------|-------------|
| `X-Request-Id` | Trace ID for log correlation |
| `Content-Type` | `application/json;charset=UTF-8` |
