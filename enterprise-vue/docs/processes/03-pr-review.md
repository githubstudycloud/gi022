# PR Review 规范

> 版本：v1.0 | 日期：2026-03-18

---

## 1. PR 提交者责任

### 1.1 PR 描述模板

```markdown
## 变更说明
<!-- 简述做了什么，为什么这样做 -->

## 变更类型
- [ ] 新功能（feat）
- [ ] Bug 修复（fix）
- [ ] 性能优化（perf）
- [ ] 重构（refactor）
- [ ] 文档更新（docs）
- [ ] 其他（chore/ci/build）

## 关联 Issue
Closes #EVS-XXX

## 测试
- [ ] 已通过本地单元测试
- [ ] 已通过本地手动测试
- [ ] 已添加相应测试用例
- [ ] 涉及 E2E 场景已更新测试

## 截图/录屏（UI 变更必填）
<!-- 放前后对比截图 -->

## 注意事项
<!-- Reviewer 需要重点关注的地方、破坏性变更等 -->

## 部署说明
- [ ] 需要环境变量变更（详见下方）
- [ ] 需要数据库迁移（运行 xxx.sql）
- [ ] 需要通知下游依赖方
```

### 1.2 PR 大小控制

| PR 大小 | 行数变更 | 要求 |
|--------|---------|------|
| 小 | < 200 行 | 推荐，Review 轻松 |
| 中 | 200-500 行 | 可接受，需要拆分说明 |
| 大 | > 500 行 | 必须拆分或充分说明 |

**原则：** 一个 PR 只做一件事。宁愿多 PR，不要一个大 PR。

## 2. Review 者责任

### 2.1 Review 时效要求

| 优先级 | 响应时间 |
|--------|---------|
| P0（Hotfix） | 1 小时内 |
| P1（Sprint 关键路径） | 4 小时内 |
| P2（普通功能） | 1 个工作日内 |

### 2.2 Review Checklist

**正确性**
- [ ] 逻辑是否正确，是否覆盖边界情况
- [ ] 错误处理是否完善
- [ ] 是否存在潜在的竞态条件

**安全性**
- [ ] 是否存在 XSS/注入风险
- [ ] 权限控制是否正确
- [ ] 敏感信息是否脱敏/不打印日志

**性能**
- [ ] 是否有不必要的重复渲染
- [ ] 大数据量处理是否有防护
- [ ] 是否有内存泄漏风险（事件未清理等）

**可维护性**
- [ ] 命名是否语义化
- [ ] 是否有必要的注释
- [ ] 是否遵循项目规范
- [ ] 是否过度设计

**测试**
- [ ] 是否有对应测试
- [ ] 测试是否覆盖了主要场景和边界情况

### 2.3 评论规范

```
# 问题严重程度前缀

[blocker] 必须修改才能合并（逻辑错误/安全漏洞）
[major]   强烈建议修改（性能/可维护性问题）
[minor]   建议考虑（代码风格/小优化）
[nit]     可选的细节（个人偏好）
[praise]  值得学习的好代码

# 示例
[blocker] 这里没有处理 token 过期的情况，会导致用户数据丢失

[major] 这个组件在超过 1000 条数据时会有性能问题，
        建议改用虚拟列表或分页

[nit] 变量名 `d` 不够语义化，建议改为 `userData`

[praise] 这个 debounce 的实现很优雅！
```

---

## 3. 合并条件

所有以下条件满足后方可合并：

1. ✅ CI 全部通过（Typecheck + Lint + Test + Build）
2. ✅ 至少 1 位 Reviewer Approve
3. ✅ 所有 `[blocker]` 评论已解决
4. ✅ 分支已 rebase 到最新 main
5. ✅ 没有未解决的对话（resolved all conversations）

---

## 4. 自动化 Review 辅助

CI 自动检查项目（无需人工）：
- TypeScript 类型检查
- ESLint 规范检查
- Prettier 格式检查
- 单元测试（覆盖率阈值）
- 构建成功验证
- Bundle Size 检查（超出预算需人工确认）
