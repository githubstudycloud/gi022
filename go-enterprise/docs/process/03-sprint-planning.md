# 迭代规划规范

**版本**: 1.0 | **更新**: 2026-03-18

---

## 1. 迭代节奏

| 活动 | 时间 | 时长 | 参与人 |
|------|------|------|--------|
| Sprint 规划会 | 每双周周一上午 | 2h | 全团队 |
| 每日站会 | 每天 9:30 | 15min | 开发+测试 |
| Sprint 评审 | 每双周周五下午 | 1h | 全团队+产品 |
| Sprint 回顾 | 每双周周五下午（评审后） | 1h | 全团队 |

---

## 2. 工作项层级

```
Epic（史诗）
  └── Story（用户故事）
        └── Task（开发任务）
        └── Bug（缺陷）
        └── Spike（技术调研）
```

### Story 格式

```
作为 {用户角色}，我希望 {功能}，以便 {价值/目的}
```

**Story 验收标准（AC）格式（Given-When-Then）**：
```
Given: 前置条件
When:  执行动作
Then:  预期结果
```

---

## 3. 工作量估算

使用**故事点（Story Points）**，基于斐波那契数列：1, 2, 3, 5, 8, 13, 21

| 点数 | 复杂度参考 |
|------|---------|
| 1 | 简单配置修改，1h 内完成 |
| 2 | 简单功能，半天内完成 |
| 3 | 标准功能，1天内完成 |
| 5 | 中等功能，2-3天 |
| 8 | 复杂功能，一周内 |
| 13 | 建议拆分为多个 Story |

**团队速率（Velocity）**：根据历史 Sprint 的完成点数动态调整，新团队初期以 20-30 点/人/Sprint 估算。

---

## 4. Definition of Ready（进入 Sprint 的条件）

Story 满足以下条件才能进入 Sprint：

- [ ] 有清晰的用户故事描述
- [ ] 有明确的验收标准（AC）
- [ ] 故事点已估算
- [ ] 无 Blocker（依赖已解决或在同 Sprint 内解决）
- [ ] 设计图/API 文档已就绪（UI/API 类需求）

---

## 5. Definition of Done（完成的标准）

Task 满足以下所有条件才算 Done：

- [ ] 代码已提交 PR 并合并
- [ ] 单元测试覆盖率达标
- [ ] CI/CD 流水线全绿
- [ ] Code Review 通过（≥2 Approve）
- [ ] 功能已在 staging 环境验证
- [ ] AC 全部通过
- [ ] 相关文档已更新
- [ ] 无高危安全扫描告警

---

## 6. 看板状态流转

```
Backlog → Todo → In Progress → In Review → Testing → Done
                     └─────────── Blocked ──────────────►
```

| 状态 | 说明 | WIP 上限 |
|------|------|---------|
| In Progress | 正在开发 | 每人 2 个 |
| In Review | 等待 Code Review | 无限制 |
| Testing | 测试验证中 | 无限制 |
