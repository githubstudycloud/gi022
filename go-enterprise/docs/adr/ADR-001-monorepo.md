# ADR-001: 采用 Go Workspace Monorepo

**状态**: Accepted
**日期**: 2026-03-18
**决策者**: 架构委员会

---

## 背景

随着微服务数量增加，各服务之间存在共享的基础库（日志、配置、错误处理等）。如何管理这些共享库是一个关键问题。

## 问题

- 各服务独立仓库时，公共库每次变更都需要发版、各服务升级依赖，效率低
- 公共库与业务代码不在同一仓库，代码审查割裂
- 本地联调需要 `replace` 指令或发版才能测试

## 备选方案

### 方案 A：独立仓库（Multi-repo）
- 每个服务和库独立 Git 仓库
- 通过版本号依赖
- **缺点**：变更传播慢，本地调试繁琐

### 方案 B：Go Workspace Monorepo（选定）
- 所有服务和库在一个仓库
- 使用 `go.work` 管理工作空间
- 每个模块保持独立的 `go.mod`
- **优点**：原子提交、统一 CI、本地调试零成本

### 方案 C：单 go.mod 大单体
- 所有代码共享一个 `go.mod`
- **缺点**：依赖耦合，无法按服务独立发布

## 决策

**采用方案 B：Go Workspace Monorepo**

理由：
1. Go 1.18+ 原生支持 `go.work`，不需要外部工具
2. 保留了每个模块独立发布的能力（各有 `go.mod`）
3. 工具链（CI、Makefile）可以轻松按服务并行构建

## 影响

- 所有 PR 在同一仓库提交，需要 CODEOWNERS 规则保护各模块
- CI 需要检测变更模块，只构建受影响的服务（使用 `git diff` 分析）
- 发布时需要为各模块打独立的 Tag（如 `libs/config/v1.2.0`）
